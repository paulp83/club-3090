About this dashboard: club-tasks

A bench of real club-3090 bug fixes, used to compare locally served models, harnesses and effort levels. The page you came from shows the live progress of the runs.

1. The question

Can a locally served model, driven by a coding agent, fix real club-3090 bugs so that the repo's own tests pass? A follow-up came from discussion #1626: does the harness (omp, Hermes) or the effort level change the answer?

2. Why a new bench

GLM-5.3-Flash and Qwen3.8-Flash-Next launched on 2026-08-26. The public coding benches I checked all predate them, so their problems could be in training data. Every task here is a PR merged after that date.

3. How it works

  • Tasks: 321 PRs merged since 2026-08-27 → 115 small enough for one session and touching scripts/tests/ → 67 whose tests fail before the PR and pass after it, offline in Docker → 20 after screening, across 9 areas.
  • Task text: the linked issue, or the PR's problem section with the fix cut out.
  • Agent: stock mini-swe-agent with a bash shell, in a no-network Docker container holding a clean checkout from before the PR. Thinking on, effort low, 100 steps, 60 minutes per task.
  • Grading: the PR's own tests, hidden from the agent, run against the agent's working tree.
  • Measures: solved; partial credit (the hidden test's checks, scaled so before-the-PR = 0 and the PR = 1); whether it edited the PR's files; regressions in nearby tests; minutes per task; solved per agent-hour.

4. What changed mid-eval

The first draw split the tasks 6 / 4 / 10: six every config solved, four that separated configs, ten nobody solved. Reading the failures showed that 8 of those 10 had hidden tests checking something the task text never states (a CLI shape, a function name, an exact message). Only 2 were genuine misses.

Each of the 8 got an Interface section written from its hidden test, and all 8 were re-run on every config. GLM IQ4_XS went from 0/8 to 6/8 on them. The old results are kept in draw1-v1/, so the final report can show what the missing details cost each model. Rows marked † on the dashboard are these 8 tasks.

5. What's running now, and why

  • Chain v2, bare mini-swe-agent (the main round): the 8 tasks that got Interface sections re-run as draw 1 on all five configs (GLM IQ4_XS and GLM avar6, ThinkingCap, Strata IQ4_XS, Strata Q4_K_XL), so each config has a full draw 1 on the revised text. Then a second draw on all 20 tasks for ThinkingCap and both Strata configs, to separate real differences from run-to-run noise. The GLM configs get one draw because each takes 10 to 20 hours. This round ends with report-agent-evals.md.
  • omp arm: the same 20 tasks through omp on ThinkingCap-27B, Qwen3.8-Flash-Next (Strata IQ4_XS) and the better GLM config. The maintainer asked on #1626 for the omp arm to cover Flash Next and ThinkingCap-27B; the GLM stays for the harness comparison.
  • Assistant tasks: 26 everyday non-coding tasks (filing, triage, summaries, scheduling) through Hermes and omp on ThinkingCap and Flash Next. It answers @henrykrinkle01's question about which model to use for everyday assistant work.
  • Effort × harness (the 2×2): low versus the top effort rung (xhigh for Qwen3.8, max for GLM), each with bare mini-swe-agent and with omp. It is the other half of #1626. ThinkingCap also gets a second omp draw at low.
  • Hard assistant tasks: the 26 base assistant tasks hit a ceiling (both models 26/26 through omp once two task bugs were fixed), so a harder set of 12 (hard-v1: long inputs, long jobs, conflicting sources, error recovery, planted instructions, changed requirements) runs as a pilot after the 2×2.
  • An omp effort bug: the first omp pass sent no effort level, so Strata ran at xhigh and GLM at max. Those runs are filed as the top-rung cells, and omp at low is re-run on both with the fixed runner.

Stage order on the page: chain v2 (re-runs and second draws) → omp → assistant → the effort runs, config by config.

7. Reading the numbers

  • With 20 pass/fail tasks, two configs need to differ by about 6 tasks to be told apart on one draw, and about 4–5 with two draws. Smaller gaps are noise.
  • Prefer the paired comparison (same tasks, McNemar) and partial credit, which have more resolution than the solve count.
  • Read tasks per hour next to the solve rate. A config that solves fewer tasks but finishes twice as many per hour can be the better daily driver.
  • Numbers on the dashboard are live and interim until a stage shows "done".
